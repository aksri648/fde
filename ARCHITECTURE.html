5. Security Architecture

🔐 FRONTEND → BACKEND

  • Bearer JWT token (or API key in dev)
  • Token contains tenant_id + owner_id
  • CORS: localhost:3000, localhost:5173 only
  • No credentials + wildcard origins
  • Rate limiting via Redis

🔑 BACKEND → APPDEVELOPER

  • X-API-Key header
  • X-Correlation-ID per request
  • X-FDE-Session-ID + X-FDE-Plan-Version
  • Idempotency-Key for safe retry
  • 30s connect/read/write timeout

🔑 BACKEND → LLMDeployer

  • X-API-Key header
  • X-Correlation-ID per request
  • X-FDE-Session-ID + X-FDE-Plan-Version
  • Two-step: create session → submit answers
  • raise_for_status() on both calls

🛡️ Tenant Isolation

  • Every query filtered by tenant_id
  • ensure_session_ownership() on all endpoints
  • 403 Forbidden on cross-tenant access
  • Audit events track all actor actions
  • Secret redaction on all logs

12. Key Design Decisions

Why Outbox Pattern?

  • Atomic state + outbox in single DB transaction
  • Worker retries with same idempotency key
  • Prevents duplicate downstream jobs/sessions
  • Max 5 attempts before HANDOFF_FAILED
  • Manual retry resets counter

Why BFF Pattern?

  • FRONTEND never calls downstream services directly
  • BACKEND owns all state transitions
  • Package transformation happens in BACKEND
  • Single auth boundary for the UI
  • CORS only configured for BACKEND

Why WS + REST?

  • REST for all mutations (safe, auditable)
  • WebSocket only for live progress notifications
  • UI refetches REST on reconnect (not event-sourced)
  • Events supplement but don't replace REST truth
  • 30s keepalive pings prevent connection drops

Why Separate Services?

  • APPDEVELOPER: app generation (SQLite, GitHub)
  • LLMDeployer: deployment orchestration (in-memory)
  • BACKEND: orchestration + persistence (PostgreSQL)
  • Independent scaling and deployment
  • Clear separation of concerns
