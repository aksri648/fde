    Note over FE,BE: Every subsequent API call:
    FE->>FE: getSessionToken() → Clerk JWT
    FE->>BE: Authorization: Bearer {clerk_jwt}
    BE->>CK: Fetch JWKS (cached 1hr)
    BE->>BE: Verify RS256 signature + exp + nbf
    BE->>BE: Extract sub → tenant_id + owner_id
    BE-->>FE: Response (tenant-scoped data)

Auth Priority Chain (BACKEND)

  • 1. Clerk JWKS verification (CLERK_JWKS_URL set)
  • 2. Static API key match (FDE_API_KEY)
  • 3. Legacy HS256 JWT (FDE_JWT_SECRET)
  • 4. Dev mode fallback (APP_ENV=development, no keys)

Multi-Tenancy

  • Clerk sub claim → tenant_id + owner_id
  • Every DB query filtered by tenant_id
  • ensure_session_ownership() on all endpoints
  • 403 Forbidden on cross-user access

14. Security Architecture

🔐 User Authentication (Clerk)

  • RS256 JWT signed by Clerk's private key
  • Verified via JWKS endpoint (public key cached 1hr)
  • Short-lived tokens (5 min), auto-refreshed by SDK
  • sub claim = user isolation boundary
  • Dev mode: bypasses when no CLERK_JWKS_URL set

🔑 Service-to-Service

  • X-API-Key header (shared secret per pair)
  • X-Correlation-ID for request tracing
  • Idempotency-Key for safe retries
  • 30s timeouts on all downstream calls
  • Keys must match: BACKEND ↔ downstream .env

🛡️ Sandbox Security

  • Secrets injected per-command (never on disk)
  • Full kernel/filesystem/network isolation
  • Ephemeral: destroyed after task completes
  • No cross-job contamination possible
  • Fallback to local when Daytona is not configured

🗃️ Data Protection

  • Tenant isolation: all queries filtered by user ID
  • Schema: create_all (never drops/truncates)
  • Secret redaction in all logs (structlog)
  • GitHub tokens: SecretStr, cleared in finally
  • No credentials in audit events or WS payloads

16. Key Design Decisions

Why Clerk for Auth?

  • Multi-user with zero auth code (hosted UI + JWKS)
  • RS256 JWTs verified without a shared secret
  • User isolation via sub claim → tenant_id
  • Graceful dev mode when unconfigured
  • OAuth/social login for free

Why Daytona Sandboxes?

  • Full isolation per task (kernel, fs, network)
  • Secrets never touch sandbox filesystem
  • Ephemeral: auto-delete prevents resource leak
  • Per-task scaling without container orchestration
  • Graceful fallback to local when unconfigured

Why LiteLLM Proxy?

  • One proxy, any model backend
  • Anthropic format everywhere (consistent SDKs)
  • Swap models with zero code changes
  • No direct Anthropic dependency in production
  • Your OpenAI-compatible key and base URL

Why Tool-Use Agent Loop?

  • Real automated deployments (not just advice)
  • Model autonomously calls cloud APIs
  • Bounded: max 12 iterations, timeout per tool
  • Live pricing via Tavily before decisions
  • Verification: tests endpoint before declaring done

Why Outbox Pattern?

  • Atomic state + delivery intent in one DB txn
  • Worker retries with same idempotency key
  • Approval returns instantly (no blocking)
  • Downstream crash doesn't lose the handoff
  • Manual retry for permanent failures

Why BFF + Microservices?

  • Single auth boundary for users (BACKEND)
  • FRONTEND never calls downstream directly
  • Each service scales independently
  • APPDEVELOPER: long-running generation
  • LLMDEPLOYER: cloud infra provisioning
